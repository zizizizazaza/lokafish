# 用户参与决策 · 需求文档（PRD v0.1）

> 范围：**仅前端**。后端接口以 mock/fixture 占位，待对齐后再接真实服务。
> 状态：草案，待评审。
> 作者：—  日期：2026-04-17

---

## 1. 背景与动机

当前 Lokafish 的仿真流水线（Ontology → Graph → Profiles → Simulation → Report）是一个"黑盒"——用户输入场景后只能等 10–30 分钟拿到最终报告，**整个决策过程不可干预**。这种模式参考了 MirrorFace 的"一键出结果"思路，但带来了几个问题：

1. **信任感弱**：用户看不到关键判断是怎么做出来的，只能接受最终结论。
2. **缺乏参与**：仿真只代表 agent 群体的"集体心智"，用户本人和外部社区的意见无处落地。
3. **同质化**：每次跑出来的结果几乎只由 LLM + 初始场景决定，缺少群体智慧的反馈回路。

**本次改版的核心主张**：把仿真过程拆成若干**决策节点（Decision Point）**，在每个节点上允许 **用户本人** 或 **外部社区** 介入投票或决策，让仿真结果体现"人机混合智能"。

---

## 2. 目标与非目标

### 2.1 目标

- **G1**：把当前线性流水线重构为**可中断的 workflow**，在关键节点暂停、等待外部输入、再继续。
- **G2**：提供 **3 种参与模式**（沙箱 / 社区 / 用户直接决策），用户在项目创建时一次性选定。
- **G3**：让用户在创建项目时可**自定义哪些节点需要介入**（决策点勾选）、以及**裁决规则**（社区票 vs 用户意见谁优先）。
- **G4**：前端实现完整的交互闭环：配置 → 启动 → 暂停在决策点 → 收集/展示意见 → 继续。

### 2.2 非目标（本期不做）

- 真正的社区系统（登录、发帖、评论、身份体系）——本期仅前端 mock。
- 后端改造——本期所有"暂停/恢复/投票聚合"逻辑用前端状态机 + 假数据演示。
- 多项目协同、跨项目投票、代币激励等治理机制。
- 移动端适配（桌面优先）。

## 3. 名词定义

| 术语 | 含义 |
|---|---|
| **Workflow** | 仿真流水线的 DAG 化表达，节点之间有依赖关系 |
| **Decision Point（决策节点）** | Workflow 中一个"可介入"的 checkpoint；默认 agent 自动推进，勾选后暂停等待输入 |
| **Participation Mode（参与模式）** | 项目级配置，决定决策节点默认行为：Sandbox / Community / User |
| **Verdict Rule（裁决规则）** | 当用户意见和社区投票同时存在时，以谁为准；或加权合并 |
| **Proposal（议案）** | 决策节点触发时系统生成的投票/表态对象，包含 agent 讨论摘要 + 候选选项 |

## 4. 参与模式（3 选 1）

项目创建时必选一种，运行过程中不可切换（切换 = 新开项目）。

### 4.1 沙箱模式（Sandbox）

- **行为**：和当前一致——仿真从头跑到尾，**用户不参与任何决策**，所有决策点由 agent 自动通过。
- **适用**：快速看 baseline 结果、demo 展示、对照组。
- **UI 特征**：项目运行页不显示决策面板，进度条一路跑到底。

### 4.2 社区模式（Community）

- **行为**：每到一个决策节点，agent 内部讨论摘要 + 候选方案被打包成 **Proposal** 推送到"社区"；社区成员投票，**投票结果作为该节点的决策**继续推进。
- **裁决规则**：
  - 默认：简单多数。
  - 可选：加权（按参与者角色/声誉，本期用 mock）、门槛票数（不达标则回退默认）。
- **适用**：希望群体智慧参与、对自己判断不自信。
- **UI 特征**：
  - 决策节点卡片显示 Proposal 详情 + 实时票数条。
  - 倒计时（如 24h mock 成 24s）过后自动结算。
  - 报告中标注"哪些节点由社区决定"。

### 4.3 用户直接决策模式（User）

- **行为**：用户在配置阶段**勾选**想要亲自介入的决策点（可选多个、可全选）。运行到勾选点时暂停，弹出决策面板，等用户作出选择后继续。
- **裁决规则**：
  - 纯用户模式：未勾选的点 agent 自动通过；勾选的点必须用户表态。
  - 可选叠加社区：勾选点同时收集社区投票作为**参考信息**展示给用户（但最终以用户意见为准）。
- **适用**：专家用户、希望高度掌控结果的场景。
- **UI 特征**：
  - 配置页有决策节点多选清单，带每个节点的说明。
  - 运行页在勾选节点暂停，全屏突出决策面板，展示 agent 讨论摘要、候选选项、可选的社区参考票数。

### 4.4 模式对比表

| 维度 | 沙箱 | 社区 | 用户 |
|---|---|---|---|
| 用户是否介入 | 否 | 否 | 是（可选节点） |
| 社区是否介入 | 否 | 是（全部节点） | 可选（仅参考） |
| 裁决方 | agent | 社区投票 | 用户 |
| 总耗时 | 最短 | 最长（等投票） | 中等（看用户速度） |
| 结果可复现 | 是 | 否 | 否 |

## 5. Workflow 与决策节点设计

### 5.1 Workflow 结构（前端视角）

把当前 5 阶段流水线进一步拆分，在每阶段内部标出**潜在决策点**（共约 6–8 个，本期至少上线 4 个）：

```
Stage 1 · Ontology
  └── DP-1  实体类型清单定稿       ← 是否接受 LLM 抽取的实体类型？漏/多要不要改？

Stage 2 · Graph Build
  └── DP-2  关键关系权重确认       ← 社区/用户可加权/删除关键边

Stage 3 · Profiles
  ├── DP-3  Agent 人群结构比例     ← 确认各类 agent 数量分布
  └── DP-4  代表性 Agent 画像审核  ← 抽样审核几个 profile 是否合理

Stage 4 · Simulation
  ├── DP-5  关键事件注入            ← 是否在仿真过程插入外部事件（黑天鹅）
  └── DP-6  争议回合结果裁决        ← 对 agent 讨论僵持的回合做仲裁

Stage 5 · Report
  └── DP-7  结论倾向性审阅          ← 报告关键结论可否直接采纳
```

> 节点清单为首版建议，需产品/算法再对齐。每个节点都支持：跳过（交 agent）、单独勾选、多选。

### 5.2 决策节点数据结构（前端 mock）

```ts
interface DecisionPoint {
  id: string;              // e.g. "DP-3"
  stage: 1 | 2 | 3 | 4 | 5;
  title: string;           // "Agent 人群结构比例"
  description: string;     // 说明这个节点在决定什么
  options: Option[];       // agent 产出的候选方案
  agentSummary: string;    // agent 讨论摘要（markdown）
  deadline?: number;       // 社区模式下的截止时间戳
}

interface Proposal {
  dpId: string;
  mode: 'community' | 'user';
  votes?: Record<optionId, number>;  // 社区模式
  userChoice?: optionId;             // 用户模式
  finalChoice: optionId;
  resolvedAt: number;
}
```

## 6. 用户故事与核心流程

### 6.1 创建项目（配置阶段）

**US-1 · 选模式**
> 作为用户，我在输入场景之后、启动仿真之前，能够从"沙箱 / 社区 / 用户"三种模式中选一种。每种模式有短说明和图示，帮我做判断。

**US-2 · 选决策点（仅 User 模式）**
> 当我选择"用户直接决策"，系统展示所有可介入的决策点清单，我可以勾选/全选/清空，每个节点有说明告诉我这里在决定什么。

**US-3 · 设裁决规则（User + 社区参考时）**
> 我可以在 User 模式下开启"同时收集社区投票作为参考"，但明确标注"最终以我为准"。

### 6.2 运行阶段

**US-4 · 沙箱：一路到底**
> 选沙箱后启动，进度条连续推进到报告生成，和今天的体验一致。

**US-5 · 社区：每个节点暂停收票**
> 选社区后启动，仿真推进到每个决策节点时**前端状态机暂停推进**（mock 计时器倒计时），显示当前 Proposal 的票数变化和截止倒计时，到期后自动用多数票结算并继续。

**US-6 · 用户：勾选点暂停请我决策**
> 选用户模式后启动，仿真推进到**我勾选过**的节点时暂停，弹出全屏决策面板：agent 讨论摘要 + 候选方案 + （可选）社区参考票 + 我的选择按钮。我提交后才继续推进。

**US-7 · 可视化决策历史**
> 进入 Analytics/Report 页时，能看到这次运行中每个决策节点"由谁决定、结果是什么、多数意见 vs 少数意见"。

### 6.3 异常/边界

- **US-8**：社区模式下，倒计时结束但票数 = 0 → 回退为 agent 自动决策，并在报告中标注"社区弃权"。
- **US-9**：用户模式下，用户长时间不决策 → 保持暂停态，不超时（本期不设上限，给配置项 placeholder）。
- **US-10**：刷新/重进页面 → 从 `backend/uploads/projects/<id>/` 或 localStorage 还原 workflow 进度和已收集的投票（本期 localStorage mock）。

## 7. 前端改动范围（概览）

### 7.1 新增屏幕 / 面板

| 位置 | 新增内容 | 说明 |
|---|---|---|
| `src/screens/input.js` | **模式选择区** + **决策点勾选清单**（User 模式时展开） | 项目启动前的配置 |
| `src/screens/simulation.js` | **决策点卡片**（社区模式实时票数 / 用户模式暂停面板） | 运行期交互 |
| `src/screens/report.js` | **决策历史时间轴** | 报告补充区块 |
| `src/components/` | `ParticipationModeCard.js`、`DecisionPointList.js`、`ProposalPanel.js`、`VoteBar.js` | 可复用组件 |

### 7.2 新增状态/数据层

- `src/lib/workflow_state.js`：前端 workflow 状态机（idle / running / paused@DP / resolved / done），负责在"到达决策点时暂停"的逻辑。
- `src/lib/participation_client.js`：和假的社区服务交互（submit vote / fetch votes / resolve proposal），本期返回 mock 数据。
- `src/data/decision_points.js`：决策节点静态定义（ID、标题、说明、候选方案模板）。

### 7.3 改动已有数据流

- `project_client.js`：`run()` 调用增加 `mode` 和 `selectedDecisionPoints` 字段；本期前端透传但不依赖后端响应（mock）。
- demo 模式（Taylor Swift）：补一份"预制投票结果"的快照，供社区模式 demo。

### 7.4 **不动**的部分

- `backend/` 全部——暂停/恢复/投票聚合全由前端状态机模拟。
- 现有五屏布局和视觉风格——在现有框架内加面板和卡片，不重构路由。

## 9. 分期与里程碑建议

| 里程碑 | 范围 | 预计交付 |
|---|---|---|
| **M0 · 架构对齐** | 确认决策节点清单、前后端契约占位、数据结构 | 1–2 天 |
| **M1 · 配置端** | 模式选择 UI + 决策点勾选 + 本地持久化 | 2–3 天 |
| **M2 · Sandbox 回归** | 改动不破坏现有沙箱行为 | 0.5 天 |
| **M3 · Community 模式（纯前端 mock）** | Workflow 状态机 + 票数 UI + 倒计时结算 | 3–4 天 |
| **M4 · User 模式** | 暂停面板 + 用户决策交互 + 可选社区参考 | 2–3 天 |
| **M5 · Report 决策历史** | 时间轴组件 + 数据贯通 | 1–2 天 |
| **M6 · Demo 资产** | Taylor Swift demo 补投票快照、对三种模式各预置一份演示数据 | 1 天 |

合计 ≈ 10–15 人日（单人工作量估算）。

## 10. 待定 / 风险

- **R1**：社区模式的"真实投票"依赖后端；首版用前端 mock 能否说服演示对象？→ 需要和产品对齐 demo 话术。
- **R2**：决策点拆分粒度容易"太碎"导致用户疲劳 → 首版先开 4 个关键点，其他节点仅显示"agent 自动通过"占位。
- **R3**：User 模式下长时间暂停会不会让人忘记项目？→ 考虑加浏览器通知或邮件提醒（本期不做）。
- **R4**：现有前端是"vanilla JS + 手写屏幕"，引入状态机会不会破坏可读性？→ 保持单文件状态机，不引入 Redux/Zustand 等库。
